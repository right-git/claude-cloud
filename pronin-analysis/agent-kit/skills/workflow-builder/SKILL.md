# Workflow Builder

Цель: из референса и/или слов пользователя получить workflow, по которому агент
**с первого раза** делает ролик нужного вида. Workflow — это не описание вкуса, а набор
измеренных чисел, правил с проверками и этапов с критериями приёмки.

Файлы скилла:
- `references/reference-analysis.md` — как разобрать видео-референс в числа.
- `references/grilling-map.md` — дерево решений для интервью (что обязательно выяснить).
- `templates/workflow-template.md` — скелет workflow §0–§13.
- `templates/companion-skill-template.md` — скелет companion-скилла.
- `templates/decisions-template.md` — журнал решений.
- `checklists/workflow-acceptance.md` — проверка готового workflow перед показом.

Общие правила проекта действуют всегда: `AGENTS.md`, `workflows/_shared/production-qa.md`
(часть A U01–U16 — нижняя планка любого workflow: новый workflow может ужесточить значения,
но не отменить правило).

## Жёсткие правила

1. **Grilling обязателен.** Этап 3 выполняется только через скилл `grilling`
   (`.agents/skills/grilling/SKILL.md`; если он установлен под именем `grill-me` — тот же
   скилл). Если скилла нет — остановиться и сказать пользователю установить его. Не
   имитировать интервью своими силами и не пропускать этап, даже если «всё понятно из
   референса»: подтверждение выводов из референса — тоже часть grilling.
2. **Числа, а не прилагательные.** В workflow нет слов «крупно», «аккуратно», «динамично»
   без числа рядом: px, секунды, hex, доли кадра, количество элементов.
3. **У каждого правила есть проверка** — чем и на каком этапе её проверить (кадр, замер,
   линтер, прослушивание). Правило без проверки не записывать.
4. **Источник у каждого решения:** `референс (vN, таймкод)` / `пользователь (дата)` /
   `стандарт проекта (U.., AGENTS.md)` / `дефолт скилла`. Пишется в `decisions.md`.
5. **Не копировать чужое:** логотипы, аватары, CTA, фирменные экраны референса не
   переносятся. Переносятся приёмы, ритм, сетка, типографика, механики.
6. **Не плодить дубли.** Перед созданием проверить `workflows/`: если существующий
   workflow подходит на ≥70%, предложить расширить его (вариант в §4/§5), а не создавать новый.
7. Канальные дефолты из `AGENTS.md` (формат 9:16, CTA, логотип канала) входят в workflow
   автоматически, если пользователь явно не сказал иначе для этого формата.

## Процесс

### Этап 0. Приём задачи (без вопросов пользователю, если всё дано)

Определить режим:
- **R** — есть видео-референс (файлы или ссылки);
- **W** — только описание словами;
- **R+W** — и то, и другое (слова пользователя приоритетнее референса при конфликте).

Собрать: рабочее название формата (slug, kebab-case), канал, язык, ссылки/файлы
референсов, всё, что пользователь уже сказал о желаемом. Проверить существующие workflow
(правило 6). Создать папку `workflows/<slug>/` и черновик `workflows/<slug>/decisions.md`
по шаблону.

Если референсов нет, а пользователь описывает чужой стиль словами («как у X») — предложить
прислать 2–5 роликов X: workflow по референсу точнее. Не блокировать работу, если откажется.

### Этап 1. Разбор референса (режим R и R+W)

По `references/reference-analysis.md`. Минимум 3 ролика, если пользователь дал столько;
если один — помечать все выводы как «по одному ролику, низкая уверенность».

Результат:
- `workflows/<slug>/reference/videos/vN.md` — покадровый разбор каждого ролика;
- `workflows/<slug>/reference/README.md` — сводка: измеренные числа (медиана и разброс по
  роликам), повторяющиеся механики, драматургия, что встречается в одном ролике (не правило),
  что не получилось измерить.

Каждое число в сводке с таймкодом-доказательством. Не угадывать: если не измерено — так и
записать, это уйдёт вопросом в grilling.

### Этап 2. Черновик решений

Пройти `references/grilling-map.md` ветка за веткой и для каждого пункта заполнить в
`decisions.md`: значение, источник, уверенность (высокая / средняя / низкая / нет).
- Высокая — измерено в ≥2 роликах одинаково, или пользователь сказал прямо, или стандарт
  проекта.
- Средняя — один ролик или разброс большой.
- Низкая / нет — догадка или пусто.

### Этап 3. Grilling (обязательно)

Вызвать скилл `grilling` и передать ему:
- цель: «согласовать спецификацию workflow `<slug>` до уровня, при котором агент сделает
  ролик без уточнений»;
- дерево решений: `references/grilling-map.md`;
- текущий `decisions.md` (что уже известно и с какой уверенностью);
- сводку референса `reference/README.md` (если есть).

Правила проведения поверх правил самого скилла `grilling`:
1. Сначала одним сообщением показать пункты с **высокой** уверенностью из референса/стандарта
   («вот что я взял из референса — поправь, если не так»). Дальше — grilling по остальным.
2. Один вопрос за раз, по веткам в порядке карты; зависимые вопросы — после тех, от которых
   зависят (например, сетка кадра — после формата и платформы).
3. К каждому вопросу — рекомендуемый ответ и почему (из референса с таймкодом / из
   стандарта / из прошлых ошибок G..). Если вопрос решается замером референса или чтением
   файлов проекта — не спрашивать, а сделать.
4. Где ответ визуальный (цвет, кегль, плотность, сетка) — показать, а не описать: кадр из
   референса, быстрый макет 1080×1920 (HTML → скриншот) или 2–3 варианта рядом.
5. Расплывчатый ответ («ну, покрасивее», «динамичнее») не закрывает пункт: переспросить до
   числа или до выбора из вариантов.
6. После каждого ответа сразу обновлять `decisions.md` (значение, источник `пользователь`,
   дата).
7. Конец grilling — когда в `decisions.md` у всех обязательных пунктов карты есть значение и
   источник, а открытых вопросов нет. Перед завершением показать пользователю итоговую
   таблицу решений одним сообщением и получить «ок».

### Этап 4. Сборка workflow

По шаблонам:
- `workflows/<slug>.md` — из `templates/workflow-template.md`. Все разделы §0–§13, ничего не
  удалять; неприменимый раздел заполнить «не используется в этом формате, потому что …».
- `assets/styles/<style>/DESIGN.md` (+ `preview.png` — сгенерированный лист стиля
  1080×1920 из реальных токенов) — только если стиль новый и переиспользуемый; иначе ссылка на
  существующий.
- `.agents/skills/<slug>/SKILL.md` — из `templates/companion-skill-template.md`: компоненты,
  команды, проверки. Политику (правила, согласования) не дублировать — она в workflow.
- В `AGENTS.md` (раздел «Workflow selection and reuse») — одна строка маршрутизации: какими
  словами пользователь просит этот формат.

### Этап 5. Самопроверка workflow

Пройти `checklists/workflow-acceptance.md`. Каждый пункт — «да» с указанием раздела, или
исправить. Не показывать пользователю workflow, пока есть «нет».

### Этап 6. Пилот (доказательство, что workflow работает)

1. Взять тестовый сценарий: от пользователя или короткий (20–30 с) по теме канала.
2. Строго по новому workflow (как будто читаешь его впервые) сделать 3 фрагмента: хук,
   самую сложную сцену формата, один переход.
3. Проверить по `production-qa.md` часть C и по §11 нового workflow, включая layout-lint и
   замер фона (`scripts/qa/layout-lint.js`).
4. Показать пользователю фрагменты + кадры покоя с наложенной сеткой + рядом кадры
   референса с тем же типом сцены.
5. Замечания пользователя → короткий повторный grilling по ним (через `grilling`, только по
   затронутым веткам) → правка workflow (правило + проверка + запись G.. в регистр, если это
   новая ошибка) → правка фрагментов. Повторять до «ок».
6. Пометить в шапке workflow: `Статус: проверен пилотом <дата>`. До этого статус
   `черновик` — по черновику полноценные ролики не делать.

### Этап 7. Сдача

Отчёт пользователю: список созданных файлов; 5–10 ключевых решений из `decisions.md`; что
осталось с низкой уверенностью и будет уточнено на первом реальном ролике; как запускать
(«Сделай видео по workflow `<slug>`: <сценарий>»).
